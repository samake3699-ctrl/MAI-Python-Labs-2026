# Отчёт по лабораторной работе № 1

## Приём работ и расширяемые анализаторы

**Траектория:** Python Core  
**Уровень:** основной  
**Язык программирования:** Python 3.10+  
**Период выполнения:** октябрь 2026 г.

### 1. Цель работы

Цель лабораторной работы — разработать основу системы онлайн-школы для приёма лабораторных работ студентов, проверки входных данных и запуска расширяемых анализаторов.

В ходе работы изучались и применялись следующие возможности Python:

- классы и `dataclass`;
- аннотации типов;
- обработка исключений;
- работа с JSON и JSONL;
- `Protocol` и композиция;
- реестр фабрик;
- контекстные менеджеры;
- модульное тестирование.

### 2. Реализация этапа А — Приём и валидация

Разработана модель `Submission`, содержащая идентификаторы работы, студента и задания, временную метку, текст, код и декларацию использования ИИ.

Модель `AIDeclaration` описывает использование инструментов искусственного интеллекта.

Для моделей используется `@dataclass(frozen=True)`, ограничивающий изменение полей после создания объекта.

Реализованы:

- разбор JSONL-файлов;
- проверка обязательных полей и типов данных;
- проверка временной зоны;
- проверка декларации использования ИИ;
- формирование структурированных ошибок с полями `code`, `field` и `message`;
- вычисление хеша содержимого;
- обнаружение дубликатов и конфликтов идентификаторов;
- хранение принятых работ в репозитории в памяти;
- интерфейс командной строки для импорта.

Некорректная строка JSONL обрабатывается как ошибка отдельной записи, не прерывая весь импорт.

### 3. Реализация этапа Б — Анализаторы

Создан контракт `Analyzer` с методом:

```python
analyze(submission, context) -> AnalysisReport
```

Контракт описан с использованием `Protocol`.

Реализованы два анализатора.

**LengthAnalyzer**

Подсчитывает количество непустых строк текста и кода. Результат содержит пояснение в `rubric_feedback`, значение `score` равно `None`.

**TemplateAnalyzer**

Находит точные совпадения строк кода с разрешённым шаблоном, вычисляет показатель `similarity` и возвращает диапазоны строк в `evidence`.

Совпадение с разрешённым шаблоном не рассматривается как доказательство нарушения.

### 4. Расширяемость архитектуры

Реализованы `AnalyzerRegistry` и `AnalysisService`.

Реестр хранит фабрики анализаторов. Центральный сервис получает нужный анализатор по идентификатору и вызывает его метод `analyze()`.

Это позволяет подключать дополнительные анализаторы без добавления условных ветвей для каждого класса в центральный сервис.

### 5. Источники данных

Реализованы два источника шаблонов:

1. `InMemoryTemplateSource` — источник данных в памяти.
2. `JSONLTemplateSource` — источник данных из файла JSONL.

Для файлового источника используется контекстный менеджер, обеспечивающий закрытие файла при выходе из контекста.

### 8. Использованные проектные решения

**Dataclass:** применяется для компактного определения моделей данных.

**Protocol:** задаёт ожидаемый интерфейс без необходимости наследования от общего базового класса.

**Композиция:** центральный сервис использует переданный реестр анализаторов.

**Реестр фабрик:** позволяет создавать анализаторы по идентификатору.

**JSONL:** позволяет обрабатывать записи построчно и сообщать об ошибках отдельных строк.

**Контекстный менеджер:** управляет временем жизни файлового ресурса.

### 9. Известные ограничения

- Репозиторий хранит данные только в оперативной памяти.
- Постоянная база данных отсутствует.
- HTTP API не реализован.
- Анализаторы выполняются синхронно.
- Сравнение с шаблонами основано на точном совпадении строк.
- Код студентов не запускается.
- В приложении не используются модели машинного обучения.
- `assignments.json` предоставлен как демонстрационный файл и не загружается автоматически.
- Внешние анализаторы через Python entry points не подключены.
- Специальный декоратор измерения времени не реализован.
